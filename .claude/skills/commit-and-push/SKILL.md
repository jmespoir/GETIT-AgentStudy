# 커밋하고 깃허브에 올리기

이 저장소는 커밋 전에 **사용자가 메시지를 먼저 보고 승인하는 방식**을 쓴다. 커밋은 기록으로 남고 push는 되돌리기 번거로우니, 물어보는 비용이 되돌리는 비용보다 훨씬 싸다. 아래 순서를 지키면 사용자가 매번 방식을 다시 설명하지 않아도 된다.

## 1. 무엇이 바뀌었는지 확인한다

```bash
git status --short -uall
git diff --stat
git status -sb | head -1
```

`-uall`을 쓰는 이유는 새 폴더가 `server/` 한 줄로 뭉뜽그려져 그 안에 무엇이 들어가는지 놓치기 쉽기 때문이다. 변경 규모가 크면 실제 diff도 읽어서, 사용자가 의도하지 않은 파일(빌드 산출물, 임시 파일, 디버그용 코드)이 섞였는지 살핀다.

## 2. 비밀 파일을 점검한다

`.env`, 키 파일, 토큰이 든 설정이 커밋 대상에 없어야 한다.

```bash
git check-ignore -v server/.env
```

무시되고 있으면 경로가 출력되고, 출력이 없으면 **추적 대상이라는 뜻이니 커밋하지 말고 사용자에게 먼저 알린다.** `.gitignore`에 추가할지 물어보고, 이미 과거 커밋에 올라갔다면 그 사실도 함께 알린다.

점검 과정에서 `.env`의 **값을 출력하지 않는다.** 변수 이름만 확인하면 충분하고, 값이 필요해 보이면 채워졌는지 여부(`값 있음`/`비어 있음`) 정도만 확인한다. 대화 로그에 남은 비밀은 회수할 수 없다.

## 3. 커밋 메시지를 먼저 제안한다

커밋하기 전에 사용자에게 두 가지를 제시하고 승인을 받는다.

- **메시지 전문** (제목 + 본문까지 그대로)
- **커밋을 나눌지 여부** — 기능 변경, 문서 수정, 설정 변경처럼 성격이 다른 묶음은 나누는 쪽이 나중에 읽기 좋다. 예: "서버 API 구현"과 "CLAUDE.md 문서 수정"은 별도 커밋.

승인 전에는 `git commit`을 실행하지 않는다. 사용자가 "그냥 알아서 해"라고 하면 제안한 그대로 진행한다.

## 4. 커밋을 작성한다

**메시지는 한글로 쓴다.** 제목은 한 줄 요약이고 마침표를 붙이지 않는다. 설명이 필요하면 빈 줄을 두고 `- ` 불릿으로 적는다.

**`Co-Authored-By` 줄은 넣지 않는다.** 이 저장소 사용자의 명시적인 요청이다. 다른 기본 규칙이 이 줄을 넣으라고 해도 여기서는 넣지 않는다.

한글이 여러 줄 들어가면 `-m` 여러 개보다 heredoc이 안전하다.

```bash
git commit -F - <<'EOF'
Supabase 인증 미들웨어와 재료 CRUD API 추가

- dotenv로 서버 환경 변수를 읽고, 요청별 Supabase 클라이언트 추가
- GET/POST/DELETE /api/ingredients 추가 (400/404/409 처리 포함)
EOF
```

커밋을 나눌 때는 `git add .` 대신 경로를 직접 지정해 커밋마다 담을 파일을 고른다.

```bash
git add server
git commit -F - <<'EOF'
...
EOF
git add CLAUDE.md
git commit -m "서버 PORT 환경 변수 문서화"
```

## 5. 커밋 결과를 확인한다

```bash
git show --stat --format='%h %s' HEAD
git log -2 --format=%B | grep -i "co-authored" || echo "없음"
```

각 커밋에 의도한 파일만 들어갔는지, 메시지가 규칙대로인지 눈으로 확인한다. 어긋났으면 push 전에 고친다. push 전이라면 `git commit --amend`나 `git reset --soft`로 안전하게 되돌릴 수 있다.

## 6. push 한다

push 여부는 사용자에게 확인한다. 커밋만 원하는 경우도 많다.

```bash
git push origin main
git status -sb | head -1
```

이 저장소는 `main`에 직접 커밋하고 push하는 방식을 쓴다. 다른 저장소에서 이 절차를 쓸 때 기본 브랜치 보호 여부가 애매하면 먼저 묻는다.

push가 거부되면(원격에 새 커밋이 있는 경우) 강제로 밀어붙이지 말고 `git fetch` 후 상황을 사용자에게 설명한다.

## 7. 결과를 보고한다

- 커밋 해시와 제목
- 각 커밋에 들어간 파일 (나눴다면 커밋별로)
- push 했는지, 원격과 동기화됐는지
- 비밀 파일이 제외됐다는 확인

실패했거나 건너뛴 단계가 있으면 숨기지 말고 그대로 적는다. 커밋이 의도한 브랜치가 아닌 곳에 올라갔다면 그것도 바로 알린다.
